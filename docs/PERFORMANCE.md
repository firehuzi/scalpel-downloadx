# 实测性能（2026-10-07，本机 Windows 11 + Python 3.12）

> 2026-10-14 追加：外网部分的绝对数字在一天内会漂移几十倍，**连接数结论要看交替对比，
> 不要看单次顺序测试**。新增的 `scripts/bench_conn.py` 就是为此做的尺子，见 §7。

所有数字都是这台机器上真实跑出来的，不是理论值。
复现命令见文末的 `scripts/bench_*.py`。

---

## 1. 本机回环：引擎与磁盘的上限

128 MB 文件，从本机 `tests/support/server.py` 服务下载（剔除网络变量）：

| 项目 | 数值 |
| --- | --- |
| 磁盘裸写（fsync） | **680.9 MB/s** |
| DownloadX 1 连接 | 49.06 MB/s（峰值 165.88 MB/s） |
| DownloadX 8 连接 | **95.24 MB/s**（峰值 144.00 MB/s） |

结论：磁盘不是瓶颈（680 MB/s）；回环上限 ~95 MB/s 主要被 Python 测试服务器
（每连接一个线程、纯 Python socket 写）与 asyncio 事件循环吃掉。
多连接在回环上有约 **1.94x** 提升，说明分片调度本身没有互相拖累。

## 2. 外网（美国 CacheFly 100 MB）

| 连接数 | 耗时 | 平均 | 峰值 |
| --- | --- | --- | --- |
| 1 | 11.78s | **8.49 MB/s** | 11.25 MB/s |
| 4 | 14.17s | 7.06 MB/s | 10.83 MB/s |
| 16 | 12.62s | 7.92 MB/s | 11.10 MB/s |

对照：同一条链接用**裸 httpx 单流**拉取是 8.29 MB/s，DownloadX 单连接 8.91 MB/s
—— 也就是说引擎本身没有引入可测量的额外开销。

结论：国际链路是瓶颈，单连接就打满了，多连接没有收益。期间服务端返回过一次
`HTTP 429`，引擎按可重试错误退避后正常下完（内容校验通过）。

## 3. 国内镜像（中科大 USTC，Ubuntu 4.5 GB ISO）

固定观测 40 秒，比较真实落盘字节数：

| 连接数 | 40s 内落盘 | 实测吞吐 | 结果 |
| --- | --- | --- | --- |
| 1 | 249.3 MB | **10.37 MB/s** | 正常 |
| 4 | 156.7 MB | 4.00 MB/s | 反复 429，重试耗尽后失败 |
| 16 | 170.6 MB | 10.55 MB/s | 大量 429 + 连接被拒 |

关键发现：**USTC 这类镜像会按并发连接数限流**（HTTP 429 / 直接断连）。
连接开得越多，越容易被拒——这正是"多连接等于更快"这个直觉的反例。

引擎当时的处理是"安全失败"：429 被正确识别为可重试错误，退避重试，
从不写坏数据。但这体验不好，于是加了**自适应降并发**（见下）。

---

## 4. 自适应降并发（本轮根据实测新增）

机制：任一分片收到 `429 / 503 / 504` 时，把该任务的并发闸门收紧一格
（下限 1），运行中的分片自然结束、新分片按新上限排队，并抛出
`task_throttled` 事件（UI 会显示 `连接 16→1（服务端限流）`）。

### 真实终验：故意用 16 连接打会限流的 USTC，下整个 Debian 13.6 netinst

```
目标：debian-13.6.0-amd64-netinst.iso   755 MB
官方 SHA-256 : 65273beed27b2df543b68b65630ba525cfbad8df2b12035732b2dff87d6664e7

[  20s]  164/755 MB  10.28 MB/s  并发=1  重试事件=19
[  40s]  354/755 MB  11.22 MB/s  并发=1
[  60s]  573/755 MB  10.67 MB/s  并发=1

状态        : completed
耗时        : 78.6s   平均 9.61 MB/s   峰值 11.22 MB/s
并发        : 配置 16 -> 实际 1（限流事件 15 次，重试 19 次）
SHA-256     : 与官方逐字节一致 ✅
```

对比修复前的同场景：4/16 连接会在重试耗尽后**失败**。现在收敛到 1 连接后
稳定跑满链路，并且交付的文件哈希与官方发布值完全一致。

## 5. 怎么选连接数

| 场景 | 建议 | 依据 |
| --- | --- | --- |
| 国内镜像站（清华 / 中科大 / 阿里 / 华为云） | 1–2 | 普遍按并发限流，多了会被 429 |
| 国外 CDN（Cloudflare / CacheFly / 各厂商对象存储） | 1–4 | 单连接就能打满，链路是瓶颈 |
| 明确允许并发、单连接被限速的站点 | 8–16 | 这类站点多连接才有真实收益 |
| 不确定 | 直接保持默认 8 | 引擎被限流时会自动降到合适值 |

## 7. 2026-10-14 复测：顺序测试会骗人

同一天、同一台机器、同一个 CacheFly 10 MB 文件：

| 顺序 | 连接数 | 耗时 | 吞吐 |
| --- | --- | --- | --- |
| 1 | 4 | 31.6s | 340 KB/s |
| 2 | 1 | 2.89s | 3.5 MB/s |
| 3 | 4 | 50.0s | 205 KB/s |
| 4 | 1 | 10.9s | 940 KB/s |
| 5 | 2 | 58.1s | 176 KB/s |
| 6 | 1 | 14.1s | 724 KB/s |
| 7 | 2 | 95.0s | 108 KB/s |
| 8 | 1 | 112s | 91 KB/s |

两个必须同时看到的事实：

1. **1 连接在三次相邻交替里都比它前面的多连接组快 4–11 倍**（2 vs 1、4 vs 3、6 vs 5）。
   如果差异只是网络漂移，后跑的那组应该更慢 —— 但每次都是单连接后跑却更快。
2. **单连接自己也在漂**：2.89s → 10.9s → 14.1s → 112s（40 倍）。

所以能下的结论只有方向：**这个 CDN 上并行连接没有收益、而且很可能有害**；
"快 10 倍"这种倍数不可信（对照：当天裸 httpx 单流也只有 2.5 MB/s）。

### 方法论修正

- 比较配置必须**交替跑**（1,2,4,1,2,4），顺序跑量到的是网络的脾气；
- 单次测量不足以下结论，要看中位数；
- 引擎的 `task_throttled` 只对**可见限速**（429/503/504）生效，**静默限流它看不见** ——
  这时唯一的办法是把初始连接数设小（1~2），或者先用尺子量一下。

### 结论与默认值

`--conn 1` 对未知站点是"永远不会错得太离谱"的选择；已知奖励并行的站点（自己的 nginx、
局域网、无单连接上限的对象存储）再往上加。`scripts/bench_conn.py` 就是你自己的尺子：

```powershell
python scripts\bench_conn.py https://example.com/big.iso --connections 1,2,4 --rounds 3
```

倍数 < 1.2 就说明加连接没换来吞吐，用 1；> 1.5 才说明并行真有用。

### 已实施：并发自校准（同任务内前后对比）

按上面的思路做进了引擎（`core/download_worker.py`）：大文件 + 配置并发 > 1 时，
先用 1 连接量一段（**前 25% 只热身，不计入速率**，排除 DNS/TLS/慢启动），
再放开到 N 连接量一段，聚合吞吐没有 1.15 倍提升就收紧回 1。
只影响还没开始的分片，正在传的连接自然结束。

三条验证（`work/verify_ramp.py` 的等价场景已固化为测试）：

| 场景 | 单连接 | 放开后 | 判定 |
| --- | --- | --- | --- |
| 本地 · 聚合限速 512 KB/s（静默限速模型） | 513 KB/s | 512 KB/s | 增益 1.00x → **退回 1** ✅ |
| 本地 · 每连接独立限速（并行真有用） | 1556 KB/s | 6174 KB/s | 增益 3.97x → **保留 4** ✅ |
| 真机 · CacheFly 100 MB，配置 8 连接 | 5106 KB/s | 3953 KB/s | 增益 0.77x → **退回 1** ✅ |

真机那行值得单独说：**8 连接比单连接慢 23%**，而且服务端不报任何错误——
这正好解释了 2026-10-14 手测时"1 连接比 4 连接快得多"的现象（当时的绝对值不可信，
但方向是对的）。这一版还用预热修掉了一个真实偏差：第一版把基线量成了 31 KB/s
（冷启动假象），进而错误地"保留 8 连接"。

代价：大文件开头多 2~6 秒测量时间（期间仍在下载，只是不并行）；小于 24 MB 的任务
完全跳过校准。参数见 README 的配置表。

注意：自适应降并发只会在**同一个任务的一轮运行内**生效。下次重新入队会从
配置的连接数重新开始学习。要做"记住某个站点的最佳并发"需要一张按 host 的
经验表，属于后续可做的事（见下）。

## 6. 复现方法

```powershell
# 回环上限 + 磁盘基线
python scripts\bench_speed.py --only-a

# 外网 / 国内镜像对比（固定观测窗口）
python scripts\bench_speed.py            # 外网多连接
python scripts\bench_mirror.py           # 国内镜像放宽/限流对比

# 真实整包下载 + 官方哈希校验
python scripts\bench_verify.py
```

压测脚本只写项目内的 `work/` 目录（已在 .gitignore 中），测完自动清理下载产物。
